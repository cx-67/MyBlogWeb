## 为什么需要 ReAct

直接让 LLM 调用工具，最大的问题是**幻觉**：模型会"编造"工具的返回结果，而不是真的去执行。ReAct（Reason + Act）的核心思路是**把"思考"和"行动"显式分离**，强制模型在每一步都先 Think，再 Act，再 Observe。

## 推理循环设计

在我的备考 Agent 平台中，循环长这样：

```
Think  → 模型输出思考过程（这一步不执行任何工具）
Act    → 解析出要调用的工具 + 参数
Observe→ 真正执行工具，把结果喂回模型
↩ 重复，直到模型输出最终答案
```

## 工程实现要点

### 1. 中断机制

用 `threading.Event` 实现可中断的流式输出。用户随时可以打断，不会卡死。

### 2. 安全退出

捕获 `GeneratorExit`，保证流式连接在异常时也能正确关闭，不泄漏资源。

### 3. 三 Agent 分工

不是一个大 Agent 干所有事，而是：
- **PlannerAgent**：拆解任务
- **RetrieverAgent**：RAG 检索
- **QuizMasterAgent**：出题批改

用**确定性 Workflow 编排**，而不是让单个 Agent 自由发挥，可控性高很多。

## 踩坑记录

1. **思考与行动混在一起**：早期没强制分离，模型经常"想着想着就以为做完了"。后来在 prompt 里用明确的 `Think:` / `Act:` 标记约束。
2. **工具参数幻觉**：模型会给工具传不存在的参数。用 `inspect.signature` 动态校验，不合法直接拒绝。
3. **死循环**：模型偶尔会反复调用同一工具。加了轮次上限 + 重复检测。

## 小结

ReAct 不复杂，复杂的是工程化：中断、退出、参数校验、防死循环。把边界情况都想清楚，Agent 才稳定。
