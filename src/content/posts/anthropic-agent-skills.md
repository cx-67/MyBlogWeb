## 一、什么是 Skill

**通俗解释**：Skill 是写给 AI 的"操作手册"——当用户说某类话时，你应该怎么做，按什么步骤，输出什么格式。

**组成**：触发条件 + 执行指令。

**核心概念**：Skill 不改变 AI 的底层能力，而是给 AI **提供上下文、规则和步骤**，让它在特定场景下表现得更专业、更一致、更省心。

## 二、创建 Skill 的迭代循环

明确需求 → 编写草稿 → 创建测试 → 运行评估 → 改进重写

**详细步骤：**

1. **捕获意图**：核心任务（需要做什么）、触发条件（关键词）、输出格式、测试用例
2. **采访与研究**：边界情况、输入输出标准、示例文件、成功标准、依赖项
3. **编写 skill.md（核心）**：

| 组成部分 | 说明 | 必要 |
|---|---|---|
| name | Skill 唯一标识符 | √ |
| description | 何时触发、做什么 | √ |
| compatibility | 需要的工具、依赖 | × |
| prompt | 具体要 AI 怎么做的步骤和规则 | √ |

## 三、Skill 的文件结构

```
my-skill/
├── SKILL.md          ← 必须：核心文件
│   ├── YAML 头部     ← name + description（必须）
│   └── Markdown 正文  ← 具体指令
└── 打包资源（可选）
    ├── scripts/      ← 可执行脚本（用于确定性/重复性任务）
    ├── references/   ← 参考文档（按需加载）
    └── assets/       ← 模板、图标、字体等输出用的文件
```

## 四、渐进式加载机制

Skill 的内容不是一次性全部加载的，而是分三个层级：

1. **元数据层**：name + description，**始终在上下文中**（约 100 词）。这是"目录"，帮助 AI 判断要不要用这个 Skill。
2. **正文层**：SKILL.md 的正文，**触发时加载**（建议 < 500 行）。这是"操作手册"的详细内容。
3. **资源层**：scripts/、references/ 等，**按需加载**（无限制）。只在真正需要时才读取，节省上下文空间。

**好处**：不用的信息不占内存，保证 AI 在大量 Skill 同时存在时也能高效运行。

## 五、SKILL.md 编写模式与技巧

### 1. 定义输出格式

直接在 SKILL.md 中写死模板，让 AI 按模板填空：

```markdown
## 报告结构
始终使用以下模板：
# [标题]
## 执行摘要
## 核心发现
## 建议
```

### 2. 用示例解释

```markdown
## 提交信息格式
**示例 1：**
输入：新增了用户认证功能，使用 JWT 令牌
输出：feat(auth): 实现基于 JWT 的认证
```

### 3. 用"为什么"代替"必须"

官方建议：**多解释原因，少用命令式**。比如不说"你 MUST 用这个模板"，而是说"使用这个模板能确保输出格式一致，方便下游工具解析"。AI 理解原因后，会做得更好。

### 4. 多领域支持模式

如果一个 Skill 要支持多个平台（比如 AWS、GCP、Azure），可以这样组织：

```
cloud-deploy/
├── SKILL.md          ← 工作流 + 选择逻辑
└── references/
    ├── aws.md        ← 只加载需要的那个
    ├── gcp.md
    └── azure.md
```

AI 会根据用户需求只读取对应的参考文件，不会把三个平台的内容全塞进上下文。

## 六、测试与评估

### 创建测试用例

想 2-3 个真实用户可能会说的话作为测试提示词，保存到 `evals/evals.json`：

```json
{
  "skill_name": "my-translator",
  "evals": [
    {
      "id": 1,
      "prompt": "帮我把这段技术文档翻译成英文",
      "expected_output": "专业的英文技术文档翻译",
      "files": []
    }
  ]
}
```

### 测试四步骤

1. **同时启动所有测试（带 Skill 和不带 Skill）**：对每个测试用例，同时发起两个子任务——一个加载了 Skill，一个没有加载（作为对照），对比 Skill 到底有没有帮助。
2. **在测试运行时起草断言**：定义"什么叫通过"的可验证标准。比如"输出文件必须包含'执行摘要'标题"、"生成的 CSV 必须有 3 列"。
3. **结果反馈时立即记录时间数据**：每个子任务完成时会返回 `total_tokens` 和 `duration_ms`。这是唯一的机会抓取这些数据，错过就没了。
4. **评分、汇总，启动查看器**：对所有结果打分（通过/失败），汇总成基准测试报告，启动网页查看器直观对比。

### 评估方式

- **定性评估**：人工判断输出质量（如"文风是否合适"、"设计是否美观"）。适合主观任务。
- **定量评估**：用可验证的断言（如"输出是否包含某个关键词"、"文件格式是否正确"）自动打分。适合客观任务。

## 七、Anthropic Agent Skills 规范（核心）

- **Skill = Prompt + Tools 的封装单元**（不是单一 prompt，也不是单一工具）
- **渐进式披露**（Progressive Disclosure）：先让 LLM 看到 Skill 的元数据（名字 + 描述），LLM 判断需要时再加载详细指令——避免 Token 爆炸
- **文件系统约定**：Skill 通过特定目录结构的 `.md` 文件定义，便于版本管理和分享

## 八、为什么使用渐进式披露

- **Token 成本控制**：假设用户有 10 个 Skill，每个 Skill 的 prompt 有 500 token，一次性加载就是 5000 token——每次对话都浪费。渐进式披露只在需要时加载，节省 60-80% Token。
- **LLM 决策准确度**：工具列表太长会让 LLM 选择困难（类似给一个人 100 个选项反而选不出来）。元数据层让 LLM 先做粗筛，再加载详细指令，决策更精准。
- **用户响应速度**：System Prompt 越短，LLM 首 token 延迟越低。
