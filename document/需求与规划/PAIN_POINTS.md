# 痛点清单

> 本文件记录在手动搭建本作品集站点过程中遇到的痛点与摩擦，作为后续 **"作品集生成助手 Agent"** 项目的需求输入。
> 每条痛点标注了【严重度】和【Agent 可解决性】，便于优先级排序。

---

## 一、内容创建类痛点

### P1. 手写 frontmatter 字段多且易错【严重度：高】【可解决性：高】

**现象**：每新增一个项目，要手写 10+ 个 frontmatter 字段（title/description/cover/tags/category/role/date/featured/liveUrl/repoUrl/documents/order），容易漏字段、写错类型、忘记路径格式。

**期望**：Agent 能通过对话引导（"项目叫什么？用了什么技术？有没有线上地址？"）自动生成符合 schema 的 frontmatter。

### P1.5 手动填清单本身就很累 —— 简历解析替代手填【严重度：极高】【可解决性：高】

**现象**：即使提供了 `REPLACE_MANIFEST.md` 替换清单，用户仍需手动填写十几项个人信息、技能、项目经历。而这些信息**绝大多数已经存在于用户的简历里**（PDF/Word）。让用户把简历内容再抄一遍到清单，是重复劳动，也是劝退点。实际体验中，本站作者填了一部分就因为"手打太累"而放弃。

**期望**：Agent 支持直接上传简历（PDF/Word），由 LLM 解析后**自动填充**清单的绝大部分字段（姓名、教育、技能、项目经历、联系方式等），用户只需做"确认/微调"而非"从零填写"。

**实现要点**：
- 简历解析覆盖度目标 ≥ 80% 字段自动填好
- 多份简历（如本作者有售前/后端/个人三版）可合并去重，让用户选择以哪版为主
- 解析结果以"可编辑清单"形式回显，用户可逐项确认/修改，而非黑箱覆盖
- 个性化字段（如站点配色偏好、座右铭）简历里没有，仍需对话补充
- 这一条是 Agent 项目 **MVP 的核心差异化能力**，直接决定产品能否"让用户 5 分钟内拿到属于自己的站点"

### P2. 封面图需要自己准备【严重度：中】【可解决性：中】

**现象**：每个项目要一张封面图，目前用占位 SVG 临时凑。真实场景下用户可能没有现成截图，或截图尺寸不一。

**期望**：Agent 能根据项目标题/技术栈生成主题色封面（类似本站的 SVG 占位图但更精致），或指导用户上传截图并自动裁剪。

### P3. 标签命名不统一【严重度：中】【可解决性：高】

**现象**：`tags` 是自由文本，"Vue3"、"Vue 3"、"vue3" 可能并存，导致标签筛选失效。

**期望**：Agent 维护一个标签词表，新增内容时做归一化/补全建议。

## 二、文档管理类痛点

### P4. 文档需手动放目录再手填路径【严重度：高】【可解决性：高】

**现象**：PDF/Word 文档要先手动放进 `public/files/`，再到 Markdown 的 `documents` 字段手填 `path`。路径写错则下载 404，且无任何提示。

**期望**：Agent 支持拖拽/选择上传文档，自动放到正确目录并生成路径引用，甚至自动识别文档名填入 `name`。

### P5. 文档无法预览/校验【严重度：中】【可解决性：中】

**现象**：放进去的 PDF 是否能正常打开、文件名是否乱码，要部署后手动点才知道。

**期望**：Agent 在构建前校验所有 `documents.path` 是否存在、文件是否可读。

### P6. 简历 PDF 替换后要记得同步【严重度：低】【可解决性：高】

**现象**：简历更新后要手动覆盖 `public/files/resume.pdf`，容易忘。

**期望**：Agent 提供"更新简历"入口，上传即替换并记录版本。

## 三、配置与部署类痛点

### P7. base 路径配置极易踩坑【严重度：高】【可解决性：高】

**现象**：`astro.config.mjs` 的 `base` 必须等于仓库名，否则本地预览和线上所有资源 404。本站在构建时就因 sitemap 插件 + site 占位报错，排查了一轮。用户（尤其非前端背景）很难自己定位。

**期望**：Agent 初始化时询问"仓库叫什么名字 / 是用户站点还是项目站点"，自动填好 `site` 和 `base`，并在 README 里说明。

### P8. 部署流程对新手不友好【严重度：高】【可解决性：高】

**现象**：要懂 Git、GitHub Actions、Pages 设置三件事。本站虽提供了 workflow，但"Settings → Pages → Source 选 GitHub Actions"这一步用户未必知道。

**期望**：Agent 生成逐步部署指引（含截图位），或直接通过 GitHub API 帮用户开启 Pages、触发首次部署。

### P9. 本地预览路径带 base 前缀，反直觉【严重度：低】【可解决性：低】

**现象**：本地 `npm run dev` 后要访问 `http://localhost:4321/MyBlogWeb/` 而非根路径，容易误以为没启动成功。

**期望**：Agent 在启动 dev 时自动打印正确访问地址。

## 四、个性化与维护类痛点

### P10. "关于"页信息硬编码在组件里【严重度：中】【可解决性：高】

**现象**：`about.astro` 的 profile/skills/timeline 是写死在组件里的 JS 对象，改信息要进代码。对非前端用户不友好。

**期望**：把这些抽成 `src/content/profile.ts` 或单独的数据文件，Agent 提供表单式编辑。

### P11. 配色/主题修改需要懂 CSS 变量【严重度：中】【可解决性：中】

**期望**：Agent 提供"换肤"对话（"我想要更偏蓝绿的配色"），自动改 `global.css` 的令牌。

### P12. 无内容预览/草稿机制【严重度：低】【可解决性：中】

**现象**：虽然有 `draft: true`，但没有"预览即将发布"的可视化流程。

**期望**：Agent 支持草稿预览、定时发布。

## 五、元数据与 SEO 类痛点

### P13. 每页的 description 要手填【严重度：低】【可解决性：高】

**期望**：Agent 根据正文自动生成 meta description。

### P14. 无 OG 图/社交分享卡【严重度：中】【可解决性：中】

**现象**：分享链接到微信/QQ 无预览图。

**期望**：Agent 自动为每篇内容生成 OG 图（标题 + 主题色）。

### P15. 文章内容无法从已有平台同步 —— 飞书 Wiki 集成【严重度：高】【可解决性：中】

**现象**：用户（本站作者）已在飞书 Wiki 写了大量技术文章与项目文档，但作品集站点的文章需要**重新手写 Markdown**。双份维护成本高，且容易遗忘同步导致内容不一致。作者明确反馈"文章展示的根本不一样"，就是因为站点文章是占位/重写的，与飞书原文脱节。

**期望**：Agent 支持**从飞书 Wiki 拉取文档**自动同步为站点文章：
- 通过飞书开放平台 API（云文档 / Wiki 节点）拉取指定空间的文档
- 转换飞书块结构为 Markdown
- 保留标题、标签、图片（飞书图片需下载转存到 public/images/）
- 支持增量同步（按更新时间），避免全量覆盖
- 用户可选择要同步的文档（而非整个空间）

**实现要点**：
- 需用户提供飞书应用 `app_id` / `app_secret`，并授权云文档读取权限
- 飞书 API 返回的是 block 结构，需写转换器
- 图片是飞书 file token，需调用下载接口转存
- 这也是 Agent 项目的**差异化能力**之一：不只是"生成"站点，还能"同步"已有内容
- 本站作者飞书 Wiki 示例：`nju4sclub.feishu.cn/wiki/...`（已用于 Pop-go 与伴侣型 AI 研究文档）

## 构建过程技术备忘

- Astro Content Collections 的 schema（zod）是强类型保障，但也是手写门槛来源 → Agent 应封装 schema。
- `getStaticPaths` 必须导出且返回 `params`，文件名带 `[]` 在某些工具链下写入会失败（本站踩过，posts/[slug].astro 首次写入 0 字节）→ Agent 生成动态路由时要校验文件完整性。
- sitemap 插件在 `site` 为占位域名时会 `reduce of undefined` 报错 → Agent 应在 site 未配置时跳过 sitemap 或给出明确提示。
- Shiki 代码高亮在 Astro 4 默认可用，无需额外配置。
