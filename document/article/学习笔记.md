#### Skill

##### 1\.什么是skill

**解释**：通俗来说，是写给AI的“操作手册”——当用户说某类话时，你应该怎么做，按什么步骤，输出什么格式。

**组成**：触发条件\+执行指令

**核心概念 ：**Skill 不改变 AI 的底层能力，而是给 AI **提供上下文、规则和步骤**，让它在特定场景下表现得更专业、更一致、更省心。

##### 2\.创建skill

**迭代循环**：明确需求 —\>编写草稿 —\>创建测试 —\>运行评估 —\> 改进重写

**详细步骤：**

1. 捕获意图：核心任务（需要做什么）、触发条件（关键词）、输出格式、测试用例（客观输出可能需要）

2. 采访与研究（问问题）：边界情况、输入输出标准、示例文件、成功标准、依赖项

3. **编写skill\.md（核心）**：

|组成部分|说明|必要|
|---|---|---|
|name|Skill 唯一**标识符**|√|
|description|何时**触发**、做什么|√|
|compatibility|需要的工具、依赖|×|
|prompt|**具体**要 AI 怎么**做**的步骤和规则|√|

##### 3\.Skill的文件结构

```Plain Text
my-skill/
├── SKILL.md          ← 必须：核心文件
│   ├── YAML 头部     ← name + description（必须）
│   └── Markdown 正文  ← 具体指令
└── 打包资源（可选）
    ├── scripts/      ← 可执行脚本（用于确定性/重复性任务）
    ├── references/   ← 参考文档（按需加载）
    └── assets/       ← 模板、图标、字体等输出用的文件
```

##### 4\.渐进式加载机制

Skill 的内容不是一次性全部加载的，而是分三个层级：

1. **元数据层：name \+ description**，**始终在上下文中**（约100词）。这是"目录"，帮助 AI 判断要不要用这个 Skill。

2. **正文层：**SKILL\.md 的**正文**，**触发时加载**（建议 \<500 行）。这是"操作手册"的详细内容。

3. **资源层：**scripts/、references/ 等，按需加载（无限制）。只在真正需要时才读取，节省上下文空间。

**好处**：不用的信息不占内存，保证 AI 在大量 Skill 同时存在时也能高效运行。（节省内存、高效）

##### 5\.skill\.md 编写模式与技巧

1. **定义输出格式：**直接在 SKILL\.md 中写死模板，让 AI 按模板填空

```Markdown
## 报告结构
始终使用以下模板：
# [标题]
## 执行摘要
## 核心发现
## 建议
```

2. **用示例解释：**

```Markdown
## 提交信息格式
**示例 1：**
输入：新增了用户认证功能，使用 JWT 令牌
输出：feat(auth): 实现基于 JWT 的认证
```

3. **用"为什么"代替"必须"：**

官方建议：**多解释原因，少用命令式**。比如不说"你 MUST 用这个模板"，而是说"使用这个模板能确保输出格式一致，方便下游工具解析"。AI 理解原因后，会做得更好。

4. **多领域支持模式：**

如果一个 Skill 要支持多个平台（比如 AWS、GCP、Azure），可以这样组织：

```Markdown
cloud-deploy/
├── SKILL.md          ← 工作流 + 选择逻辑
└── references/
    ├── aws.md        ← 只加载需要的那个
    ├── gcp.md
    └── azure.md
```

AI 会根据用户的需求，只读取对应的参考文件，不会把三个平台的内容全塞进上下文。

##### 6\.测试与评估

1. **创建测试用例：**

想 2\-3 个真实用户可能会说的话作为测试提示词，保存到 `evals/evals.json`：

```JSON
{
  "skill_name": "my-translator",
  "evals": [
    {
      "id": 1,
      "prompt": "帮我把这段技术文档翻译成英文",
      "expected_output": "专业的英文技术文档翻译",
      "files": []
    }
  ]
}
```

2. **测试四步骤**

    1. 同时启动所有测试（带 Skill 和不带 Skill）：对每个测试用例，**同时**发起两个子任务：一个加载了你的 Skill，一个没有加载（作为对照）。这样能对比出 Skill 到底有没有帮助。

    2. 在测试运行时，起草断言：利用等待时间，定义"什么叫通过"的**可验证标准**。比如："输出文件必须包含 '执行摘要' 标题"、"生成的 CSV 必须有 3 列"。

    3. 结果反馈时，立即记录时间数据：每个子任务完成时会返回 `total_tokens`（用了多少 token）和 `duration_ms`（花了多少毫秒）。**这是唯一的机会**抓取这些数据，错过就没了。

    4. 评分、汇总，启动查看器：所有测试跑完后，对每个结果打分（通过/失败），汇总成基准测试报告，然后启动一个网页查看器，直观对比结果。

3. **评估**

    - 定性评估：**人工判断**输出质量（如"文风是否合适"、"设计是否美观"）。适合**主观**任务。

    - 定量评估：用**可验证的断言（**如"输出是否包含某个关键词"、"文件格式是否正确"）自动打分。适合**客观**任务。

##### 7\.Anthropic Agent Skills规范（核心）

- Skill = Prompt \+ Tools 的封装单元（不是单一prompt，也不是单一工具）

- **渐进式披露**（Progressive Disclosure）：先让LLM看到Skill的元数据（名字\+描述），LLM判断需要时再加载详细指令——避免Token爆炸（主要借鉴）

- 文件系统约定：Skill通过特定目录结构的`.md`文件定义，便于版本管理和分享

##### 项目拷打

###### “会话与工具管理”模块

**问：**

1. 你说做了"工具的启用/禁用及参数配置"，这个工具配置的粒度是什么？是全局开关还是按用户/按会话？

2. 你提到的"前置校验与降级容错（网络失败→本地知识库）"——触发降级的判断条件是什么？为什么选择降级到本地知识库而不是直接报错？

**答：**

第一，工具配置粒度分两层：

- 全局工具层：联网搜索和知识库检索，这两个是所有用户默认可用，但用户可以在对话界面手动开关，粒度是用户级。

- Skill专属工具层：智能出题、补漏分析、网页阅读、精准计算、导出文件，这5个工具只有在用户激活某个Skill时才会被动态注册到该会话的工具列表里，粒度是Skill级。

这样的设计是为了平衡灵活性和可控性——基础检索能力人人可用，专业能力按需激活，也避免工具列表过长导致LLM选择困难。

第二，关于检索降级策略（这里我简历表述不够准确，实际实现是这样）：

我们的检索优先级是 本地知识库 → 联网搜索，判断逻辑分三步：

1. 先对用户问题做向量检索，在用户上传的教材库中找Top\-K相关片段

2. 如果相似度低于阈值（说明本地没覆盖这个topic），则检查联网搜索开关

3. 开关开启→调用联网搜索补充；开关关闭→记录到失败日志，并给用户明确反馈"该问题需联网搜索，请开启相关功能"

为什么先本地后联网？ 三个原因：

- 准确性：用户上传的教材是备考指定资料，答案权威

- 延迟：本地向量检索\<10ms，联网搜索2\-5秒

- 成本：本地检索**零API成本**，联网搜索有**调用费用**

失败记录我们会持久化到数据库，用于后续分析用户的高频未覆盖问题，反向指导知识库扩充。

###### "Skill扩展"模块

**简历："参考Anthropic规范，支持用户自定义Skill（prompt\+工具）的上传、开关及动态注册"**

**问：**

1. 你说的"参考Anthropic规范"具体指的是什么？你是怎么了解到这个规范的？

2. "动态注册"在工程上是怎么实现的？用户上传一个Skill后，下一次对话这个Skill的工具是怎么"注入"到LLM的Function Calling里的？请讲清楚从"用户点击上传"到"LLM能调用该工具"的完整链路。

**答：**

1. 我是在老师教学时提供对应的github链接，自己课后了解的Anthropic Agent Skills规范，借鉴的核心是**渐进式披露思想**——不让所有Skill的完整指令一次性塞进System Prompt，而是先注入元数据让LLM知道有哪些能力可用，被触发时再加载正文。

为什么使用渐进式披露：

- **token成本控制**：假设用户有10个Skill，每个Skill的prompt有500 token，一次性加载就是5000 token——每次对话都浪费。渐进式披露只在需要时加载，节省60\-80% Token。

- **LLM决策准确度**：工具列表太长会让LLM选择困难（类似给一个人100个选项反而选不出来）。元数据层让LLM先做粗筛，再加载详细指令，决策更精准。

- **用户响应速度**：System Prompt越短，LLM首token延迟越低。

2. 动态注册时，前端会给用户一个skill创建界面模板，用户点击上传后，通过api将该skill的对应值传给后端并调用skill创建函数，向数据库里的skill表插入一条新记录，tools字段以json数组通过SQLite进行持久化; 进行对话前，前端加载完整的skill列表，用户进行相应的勾选，用户发送信息时，request body会携带对应的selected skills; 请求到达时，后端会构建相应的System prompt，收集所有启用的工具名，然后使用渐进式披露将元数据和具体指令分别注入到system prompt中，然后使用三层工具过滤，即按照Always\_on（工具列表）、global、skill的顺序加入到active skill列表中，最后将active skills传到LLM的Function Calling中

###### "学习计划生成"模块

**简历："Agent根据用户目标与知识库输出三阶段计划，前端可拖拽编辑"。**

**问：**

1. 这个"三阶段计划"是固定的三阶段（如基础/强化/冲刺），还是LLM动态划分的阶段？如果是LLM动态划分，你怎么保证阶段划分的合理性？

2. 用户在前端"拖拽编辑"后，计划被修改了，后端如何感知这个修改并影响后续Agent的行为？换句话说，用户改了计划，Agent在后续对话中是怎么"记住"这个修改的？

**答：**

1. 我们的学习计划生成部分是由LLM动态划分的，

    为了控制LLM输出可控性，我们用了三类约束：

    - 结构约束：天数连续、每阶段≥3任务、最后任务非空——保证输出格式可用

    - 语义约束：阶段标题必须来自资料知识点、禁止模糊词——保证内容有意义

    - 业务约束：薄弱点专项1\-2天、基础到进阶递进——保证符合备考逻辑

    我们通过LLM动态划分，可以更灵活的应对用户的需求，并且通过约束，可以保证LLM划分时的合理性和稳定性。

2. 用户拖拽修改顺序后，前端put api使用plan里的对应的subject id字段下的json文件来记录修改后的表格，并调用后端的save plan\(\)将整个计划json覆盖写入，计划json的修改不会自动注入到system prompt中。

    Agent的行为会通过以下3个机制受影响：

    - 第一是计划生成时的对话历史

    - 第二是记录当前阶段和阶段目标的Working Memory

    - 第三是当智能补漏工具检测到薄弱点时，会标记目前计划需要调整，Agent在回复用户末尾会加上建议前往学习计划页面触发重规划。用户触发重规划后，前端post 对应subject下的replan，后端调用replan\(\)函数加载当前计划，从用户profile获取薄弱点，调用计划生成函数进行重规划，并用新的计划json覆盖写入

    这3个机制有优先级：

    - Working Memory是当前状态的唯一真相源（single source of truth）

    - 对话历史只做辅助参考。如果用户改了计划，下次对话时Agent会以Working Memory里的最新阶段为准，不依赖对话历史——避免旧记忆污染

#### 面试第二轮整理

##### 大模型/Agent技术体系

###### Agent架构性能权衡

**问:**

你的项目用了ReAct模式，还做了Think/Act分离。我想深挖几个点：

1. 你说"Think阶段用空工具列表（tools=\[\]），Act阶段用完整工具列表"——为什么不直接用传统的ReAct一次调用搞定？ Think/Act分离的代价是多了一次LLM调用，延迟翻倍，你是怎么权衡这个代价的？

2. 如果用户问了一个简单问题，比如"今天天气怎么样"——你的Agent会走完整的Think→Act→Observe循环吗？ 还是有什么短路机制避免不必要的开销？

这道题考察你对Agent架构性能权衡的理解，是售前岗常被客户追问"为什么这么设计"的典型问题。

**答：**

1. 传统 VS 分离：

    1. 传统ReAct的问题是Reasoning和Acting在同一个LLM调用里，LLM容易在推理过程中"脑补"工具的返回结果——比如它会输出"搜索结果显示考研数学包括高数、线代、概率"，但实际它根本没有调用搜索工具。我们的Think/Act分离通过Think阶段不给工具（tools=\[\]），强制LLM只能思考"我该做什么"，不能脑补"工具返回了什么"，从根源上杜绝了这类幻觉。Think和Act分离后，我们通过 SSE 把思考过程实时推送给前端，让用户可以知晓Agent的思考和行动的过程，提高透明度。

    2. 多一次LLM调用我们的代价不是延迟翻倍，而是增加大概20%\-30%左右，这是因为我们在Think和Act的max\_tokens的设计有所不同，think的max\_tokens只有200，大约1\-2句中文，实际耗时约0\.5\-1s，act的max\_tokens为4000，实际耗时约为2\-8s，用额外增加的20%\-30%的开销换取LLM工具调用的准确性，思考过程的透明化以及避免幻觉，我认为这是值得的。

    3. 目前Think阶段是每轮都做，但其实可以进一步优化——如果上一轮的Observe结果已经明确指向下一步行动，可以跳过Think直接Act。比如Agent搜索完知识库，Observe结果相关性很高，这时Think'我该不该用这个结果回答'其实是浪费的。我们目前没做这个优化，因为Think的200 token成本可接受，但这是未来性能优化的方向。

2. 如果用户问“今天天气怎么样”，我的Agent会走完整的Think\-Act\-Observe循环，第一轮think时解析用户需求是获取今天天气，需要调用联网搜索工具，act调用联网搜索工具，返回结果，observer将结果注入message，第二轮think已获取结果，可直接返回，无需调用工具，act直接输出天气给用户，由于think的max\_tokens只有200，两轮think的总耗时不到1s，用户体验上，Agent 先搜索再回答，我认为这是合理的流程。如果需要增加短路机制，我认为可以将短路机制分两层：

    - 第一层：闲聊短路——50 token判断，如果是打招呼/闲聊，直接用V3模型生成回复，不传工具列表（tools=\[\]），避免LLM误调工具

    - 第二层：简单问答短路——如果是常识性问题（如'1\+1等于几'），跳过Think但保留Act，Act阶段只传知识库工具（不传联网搜索），减少工具选择空间
