### 3\.3 定价洞察



- 中国模型与美国模型的价格差距可达 **60%\-90%**，同等能力下中国模型**API调用成本**远低于美国模型

- 但中国模型在极端复杂任务上与美国前沿模型仍有约 **6\-9个月** 的技术差距

- 对大多数日常任务（文案、翻译、客服、知识问答），中国模型已完全胜任，成本优势显著

- 企业落地真正需要关注的是 **总拥有成本**（TCO），包括推理成本、人工返工成本、模型切换成本

## **一、大模型基础（高频必考）**

### **Q1：什么是大模型？它与传统机器学习模型的主要区别是什么？**

**面试回答框架**：

大模型（Large Language Model, LLM）是指**参数量**通常在**数十亿到数千亿级别**的**深度学习模型**，基于 **Transformer 架构**，通过海量文本数据的自监督预训练获得强大的语言理解和生成能力。

**与传统的区别**：

|维度|传统 ML 模型|大模型|
|---|---|---|
|参数量|百万\-千万|十亿\-万亿|
|训练方式|有监督，单任务|自监督预训练 \+ 多任务微调|
|泛化能力|单一任务|零样本/少样本多任务|
|部署方式|独立部署|API 调用或本地推理|
|数据需求|标注数据|海量无标注文本|



**结合项目**：

> 在我们的备考 Agent 中，我们使用 DeepSeek 大模型作为核心推理引擎。它不是简单的"分类器"，而是能理解用户复杂的备考问题、自主决定调用联网搜索还是知识库检索、生成学习计划的多任务智能体。我们选 DeepSeek 的原因：API 兼容 OpenAI、中文能力强、性价比高。
>

### **Q2：Transformer 的 Self\-Attention 机制是什么？为什么需要除以根号 d\_k？**



**面试回答框架**：



Self\-Attention 的核心公式：`Attention(Q, K, V) = softmax(Q·K^T / √d_k) · V`



\- **Q（Query）**：当前 token 想要**查询**什么

\- **K（Key）**：其他 token 提供什么信息

\- **V（Value）**：其他 token 的实际内容

\- **除以 √d\_k**：防止点积值过大导致 softmax 梯度消失。当 d\_k 很大时，Q·K^T 的方差约为 d\_k，除以 √d\_k 将方差归一化到 1



**结合项目**：

> 在我们的项目中，虽然不直接写 Transformer 代码，但理解 Self\-Attention 帮助我理解了为什么 LLM 能处理长上下文、为什么需要滑动窗口机制、以及为什么我们在 ContextManager 中设计了摘要压缩策略——当对话超过窗口大小（5 轮），历史轮次的信息衰减会严重影响回答质量。

### **Q4：Prompt Engineering 你是怎么做的？**

## **二、Agent 架构（核心高频）**



### **Q5：什么是 AI Agent？它和传统 Chatbot 有什么区别？**



**面试回答框架**：



**Chatbot**：用户输入 → LLM 推理 → 输出文本。被动问答。



**Agent**：用户输入 → LLM 推理 → 决定用什么工具 → 执行工具 → 观察结果 → 决定下一步 → 循环直到目标达成。**自主决策 \+ 行动能力**。



**我们的 Agent 实现**：



```Plain Text
Think（思考）→ Act（行动）→ Observe（观察）→ Think → ...
```



- Think 阶段：LLM 分析用户意图，决定下一步做什么（tools=\[\]，纯思考）

- Act 阶段：LLM 决定调用工具 or 直接回复（tools=active\_tools）

- Observe 阶段：执行工具，将结果返回 LLM，继续下一轮

**与 Chatbot 的本质区别**：Agent 不是"一问一答"，而是"多轮自主循环"。用户说"帮我制定考研计划"，Agent 会自主调用搜索工具查大纲、调用知识库检索资料、生成计划、用计算工具校验时间分配。



---



### **Q6：Agentic Loop 是什么？画一下流程？**



**面试回答框架**：



Agentic Loop 就是 Agent 的"工作流水线"，核心是 **Think → Act → Observe 循环**。



**我们的实现**（代码级）：



```Plain Text
用户: "考研数学应该怎么复习？"

Round 1:
  Think → "用户想知道考研数学的复习方法，我先搜索一下最新大纲"
  Act   → tool_call: web_search("考研数学 2025 大纲")
  Observe → 搜索结果: "考研数学一包括高数、线代、概率..."

Round 2:
  Think → "已获取大纲信息，我可以直接回答用户了"
  Act   → 生成回复: "考研数学一涵盖三个模块..."
  → 无 tool_call，循环结束 → done
```



**关键设计**：

- 最多 10 轮循环（防止无限循环）

- 中断机制：前端断开连接时自动停止所有 LLM 调用

- Think 和 Act 使用不同的 System Prompt（Think 更偏推理，Act 更偏行动）

---



### **Q7：ReAct 模式和 Function Calling 的关系？你是怎么实现的？**



**面试回答框架**：



**ReAct**（Reasoning \+ Acting）是一种 Agent 设计模式，核心思想是：LLM 先推理（Reasoning）再行动（Acting），交替进行。



**Function Calling** 是实现 ReAct 中"Acting"部分的技术手段——LLM 通过 Function Calling 协议决定调用哪个工具。



**我们的实现**：

1. Think 阶段：调用 LLM 时 `tools=[]`（空工具列表），让 LLM 纯思考，输出推理过程

2. Act 阶段：调用 LLM 时 `tools=active_tools`（经过三层过滤），让 LLM 决定是否调用工具

3. 如果 LLM 返回 `tool_calls` → 执行工具 → 将结果返回 LLM → 继续下一轮

4. 如果 LLM 只返回文本 → 循环结束，输出最终回复

**与传统 ReAct 的区别**：我们做了 Think/Act 分离——Think 用空工具列表让 LLM 专注推理，Act 用完整工具列表让 LLM 专注行动。这比传统的"一次调用同时思考和行动"更可控。



---



### **Q8：Multi\-Agent 你是怎么设计的？**



**面试回答框架**：



我们实现了 Multi\-Agent 分工架构，将单体 Agent 拆分为 3 个专职 Sub\-Agent：



\- **PlannerAgent**：制定和调整备考计划

\- **RetrieverAgent**：知识检索（搜索 \+ RAG）

\- **QuizMasterAgent**：生成和评估测验



**编排模式**：确定性 Workflow（Plan → Retrieve → Quiz → Evaluate）



**通信方式**：Python 内部方法调用（\`AgentMessage\` 数据类），包含 \`sender\`、\`receiver\`、\`correlation\_id\` 等字段



**设计思考**：

- 为什么不用 LangChain/LangGraph？项目初期评估后选择自研，因为团队需要深度理解 Agent 原理，而不是依赖框架的黑盒

- 为什么用确定性 Workflow 而非自治循环？备考场景的流程是固定的（先规划→再检索→再出题），不需要 Agent 自主协商

## **三、RAG 检索增强（高频必考）**



### **Q9：什么是 RAG？为什么需要 RAG？**



**面试回答框架**：



**RAG**（Retrieval\-Augmented Generation）的本质：让大模型在回答问题之前，先去外部知识库里检索相关资料，然后基于这些资料来生成回答。



**为什么需要 RAG？**



|大模型痛点|表现|RAG 如何解决|
|---|---|---|
|幻觉|编造不存在的事实|基于检索到的真实文档回答|
|知识截止|不知道训练数据之后的信息|知识库可随时更新|
|领域知识不足|不了解企业内部文档|接入私有数据|
|无法溯源|不知道回答依据是什么|可追溯引用来源|



**我们的 RAG 实现**：

1\. **离线**：PDF 上传 → pdfplumber 提取文本 → 分块 → Embedding 向量化 → ChromaDB 存储

2\. **在线**：用户提问 → 向量检索 → 结果注入 System Prompt → LLM 生成

3\. **工具集成**：\`rag\_knowledge\_search\` 注册为 LLM 可调用的工具，Agent 自主决定何时检索



---



### **Q10：RAG、微调（Fine\-tuning）、长上下文有什么区别？怎么选？**



**面试回答框架**：



|维度|RAG|微调|长上下文|
|---|---|---|---|
|核心作用|注入外部知识|改变模型行为风格|扩大单次输入窗口|
|知识更新|随时更新知识库|需重新训练|更新输入内容|
|成本|低|中高|按 Token 计费|
|幻觉控制|较好|一般|取决于上下文信息量|
|适用场景|知识密集型问答|特定格式输出|全文分析|



**我们的选择**：

- 主体用 RAG（用户上传教材，随时更新知识库，成本低）

- 不用微调（学生项目，微调成本高且知识更新不灵活）

- 长上下文作为补充（ContextManager 中的对话历史窗口）

---



### **Q11：如何提升 RAG 的检索准确率？**



**面试回答框架**（结合项目经验）：



1\. **分块策略**：不是简单按字数切分，而是按 PDF 的自然段落/章节切分，保证语义完整性

2\. **Embedding 模型选择**：使用中文优化的 Embedding 模型

3\. **混合检索**：向量检索 \+ 关键词检索（BM25），互补提升召回率

4\. **Rerank 重排序**：对初步检索结果用 Cross\-Encoder 精排

5\. **元数据过滤**：按 subject\_id 过滤，只检索当前科目的资料



**我们踩过的坑**：

- 最初 PDF 按固定 500 token 切分，导致一个知识点被切成两段，检索效果差

- 改为按段落切分后，准确率明显提升

## **四、工具调用与 Function Calling**



### **Q12：Function Calling 的实现细节？如何防止 LLM 幻觉调用？**



**面试回答框架**：



**实现**：

1. 工具注册：定义 JSON Schema（name、description、parameters）

2. 传递给 LLM：`tools=[{...}, {...}]`

3. LLM 返回 `tool_calls`：解析 `function.name` 和 `function.arguments`

4. 执行工具：`_execute_single_tool(tool_name, args)`

5. 结果返回 LLM：`messages.append({"role": "tool", "content": result})`

**防止幻觉的 4 层策略**：



|层|策略|项目实现|
|---|---|---|
|1|三层过滤|ALWAYS\_ON\_TOOLS / GLOBAL\_TOOLS / Skill 专属|
|2|禁用通知|`"⚠️ 以下工具当前已被关闭：联网搜索。不要尝试调用。"`|
|3|RecoveryEngine|工具执行失败时自动降级，记录失败原因|
|4|ReflectionStore|跨运行记录策略成功率，排序优化|



---



### **Q13：工具执行失败怎么处理？**



**面试回答框架**：



我们实现了 `RecoveryEngine` \+ `ReflectionStore` 的容错机制：



1\. **RecoveryEngine**：包裹每个工具执行，失败时自动尝试替代策略

- 搜索失败 → 尝试用缓存结果

- 计算失败 → 尝试用简化公式

- 多次失败 → 返回明确的错误信息给 LLM

2\. **ReflectionStore**：跨运行持久化策略效果

- 记录每次恢复策略的成功/失败

- 后续调用按历史成功率排序（80% 成功率 \+ 20% 探索奖励）

- 注入 System Prompt 优化 LLM 决策

**面试亮点**：这是"反思记忆"（Reflection Memory）的具体实现，类似 Reflexion 论文的思想——Agent 从失败中学习。

### **Q16：大模型部署的性能优化怎么做？**

## **七、行为面试 \& 综合能力**



### **Q18：项目中遇到的最大技术挑战是什么？怎么解决的？**



**面试回答框架**：



**挑战：SSE 流式对话中 Think/Act 分离 \+ 工具调用 \+ 中断机制**



最初我们实现的是传统的 ReAct 循环（一次 LLM 调用同时思考和行动），但遇到两个问题：

1. 思考过程太长，用户等待体验差

2. LLM 在思考时"脑补"了工具结果，导致幻觉

**解决方案**：

1. 将 Think 和 Act 分离为两次独立的 LLM 调用

2. Think 阶段用空工具列表（tools=\[\]），让 LLM 专注推理

3. Act 阶段用完整工具列表，让 LLM 专注行动

4. 加入 threading\.Event 中断机制，前端断开时停止所有调用

**结果**：思考过程变得可控，幻觉明显减少，用户可以看到 Agent 的"思考过程"，体验更好。

## 九、智能备考 Agent 系统（Python/Flask \+ Vue 3 \+ LLM）\| 后端负责人

**2025\.05 \- 2025\.06** \| 6 人团队项目

**项目概述**：从零搭建基于大模型的智能备考 Agent 产品，用户通过自然语言对话完成备考规划、知识检索、智能练习、薄弱补漏全流程。我负责后端全链路设计与实现，交付 30\+ API 端点、7 个 Function Calling 工具、6 个数据库模块，完整覆盖 Agent 产品化技术栈。

**技术方案设计**：

- **Agent 架构**：设计并实现 ReAct 推理循环（Think→Act→Observe），将 LLM 推理分为"纯思考"和"带工具执行"两个阶段，思考阶段分离 `tools=[]` 空工具列表防止幻觉，最多 10 轮循环防止无限调用

- **Multi\-Agent 编排**：设计 PlannerAgent / RetrieverAgent / QuizMasterAgent 三 Agent 分工体系，采用确定性 Workflow 编排模式，通过 AgentMessage 数据类实现 Agent 间通信

- **RAG 检索增强**：设计 PDF 上传→pdfplumber 文本提取→按段落分块→Embedding 向量化→ChromaDB 存储的全链路方案，在线检索结果注入 System Prompt 驱动 LLM 生成，按 subject\_id 元数据过滤提升检索精度

- **LLM 选型与适配**：封装 LLMWrapper 统一适配 DeepSeek/OpenAI/智谱多厂商，通过 OpenAI 兼容 API 协议实现零成本切换，选型依据：DeepSeek 中文能力强、成本为 GPT\-4 的 1/10、API 兼容性好

**核心模块实现**：

- **三层工具过滤体系**：设计 ALWAYS\_ON / GLOBAL / SKILL 三层工具权限模型，结合前端 toggle 面板和 Skill 声明实现"按需启用、最小权限"，关闭工具时 System Prompt 注入警告防止 LLM 幻觉调用

- **Anthropic Skills 兼容**：参考 Anthropic Agent Skills 规范实现渐进式披露（元数据→完整指令），支持双来源 Skill（文件系统 SKILL\.md \+ 用户自定义），Skill 可声明专属工具列表

- **流式对话 SSE**：实现 Think→Act→Observe 全流程 SSE 流式推送，支持 threading\.Event 中断机制，过渡句智能检测过滤，用户在对话中实时看到 Agent 推理过程

- **跨对话知识共享**：设计泛型知识条目模型（错题/笔记/收藏），支持多维度过滤（关键词/类型/科目/分页），对话时通过 referenced\_knowledge 参数自动注入 System Prompt

**客户价值与效果**：

- 学生通过自然对话即可完成备考全流程，减少信息检索时间约 70%

- 支持 PDF 资料库导入，Agent 基于真实教材回答，降低幻觉率

- 自动出题\+批改\+补漏分析，替代教师手动出题环节

- 知识条目跨会话复用，学生可积累个人知识库
